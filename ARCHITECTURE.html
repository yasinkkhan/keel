Keel · architecture reference

How keel works

The shape of the system, the control flow, and where each rule is actually enforced. DESIGN-CHARTER.md records why each rule exists; this page records how it fits together.

Orientation

Keel is a Claude Code plugin marketplace, cloned wherever you keep it. Every real project is a sibling folder with its own keel.json. Keel is the tooling; it is never the work.

It exists because a plan held only in a conversation does not survive compaction, a new session, or three months. So the plan lives in files, the record lives in a state file the wrapper alone writes, and every claim about live state is re-measured rather than recalled.

The one sentence that predicts most of the design

A gate is three facts: the artifact exists, the artifact conforms, and the verdict was recorded — and when the state file and the conversation disagree, the state file is right. Almost every structure below follows from taking that seriously.

Only keel-plan-project may run outside a project folder, because it is the one that creates the folder. Everything else refuses without a keel.json.

The active project is resolved by walking up from the working directory. It is never stored, so opening a folder is selecting the project, and two windows on two projects cannot confuse each other.

Four roles, a closed set. Depth is free; roles are not. Containment nests as deep as a project needs; what is constrained is what each role may contain.

The pipeline

Eight stages, in order, for every phase in every project — whoever the actor is.

GateArtifact and the contract the wrapper checksVerdicts
groundgrounding.md — must carry Measured: and Not read:DONE
investigateinvestigation.md — must carry Positive control:DONE · BLOCKED
planplan.md — must carry Changes:; approved by the human in chatAPPROVED · REJECTED
implementactor-dependent. agent: one changes-<repo>.patch per declared repo. self/external: act-log.md with Done by: and Done on:DONE
verifyverify-report.md — a row per check, each with run-by:, plus Positive control:PASS · FAIL · INCONCLUSIVE
humanchat approval, shown the change set and the advisor question ledgerAPPROVED · REJECTED
enactenact-record.md — -Reversible and -Observable required before the actDONE · N/A · DEFERRED
recorddelivery-record.md — the phase id in uppercase, one evidence reference per declared repoDONE
enact is the gate that carries the weight

It is the irreversible outward act: filing a return, signing, sending funds, publishing, broadcasting, deploying. An act that is irreversible and currently unobservable cannot be recorded DONE — the wrapper exits 95 and tells you to record DEFERRED and hold until the outcome can be read. Answer for the act in front of you, never from what a similar act was last time.

Actors

A phase declares who acts. The actor selects what evidence a check accepts — never which gates run. The moment human work gets a lighter pipeline there are three pipelines, and the rarely-run ones are the ones handling irreversible real-world acts.

ActorWhoEvidence a check acceptsVerify means
agentClaudecommand output, a patch, a headless render, a live queryre-run it in a fresh context
selfyouan artifact you point at: a confirmation number, a filed document, a dated screenshot, a transaction hashinspect the evidence; uninspectable is INCONCLUSIVE, never PASS
externalaccountant, auditor, counsel, exchangethe received deliverable, plus who sent it and wheninspect the deliverable — "they confirmed it" is not evidence

An external phase spends most of its life waiting, which is a first-class state: it must name who and a review date, or the wrapper refuses it. A wait with no review date is an abandoned phase wearing a status.

Where each rule is enforced

Four rungs. A rule climbs one rung only after it has actually failed at its current one, with the failure cited. Hardening a gate that has never leaked is how a solo system acquires ceremony, and ceremony gets routed around at 11pm.

1 · nudge
keel-session-start.ps1 surfaces overdue phases, waits due for review, escalations, unclaimed goals and unpushed signals. Silent when clean. It never blocks.
2 · skill prose
The judgement that cannot be mechanised: when something is an epic, whether a check can fail, whether this is debt repayment or over-engineering. Prose is where taste lives — and is deliberately not where always-rules live.
3 · exit code
Anything that must always hold. The wrapper refuses and returns nonzero. Prose-only enforcement of an always-rule is a known failure mode: a model asked to count its own retries will decide this attempt is different.
4 · PreToolUse block
One rule only: plugins/** cannot be edited without DESIGN-CHARTER.md having been read this session. Repo-local, so it taxes this repo and not every session everywhere. Fails open.
ExitThe wrapper refused because
2iteration cap reached — nothing was incremented or created
89another keel command was writing the same project or the signal store: it held the lock past the ten-second wait, or a file changed after this command read it. Nothing more was written; re-run the command
90bad argument, invalid id, or an attempt to change something immutable (a delivered phase)
91no project resolved, or no state for it
92duplicate run order — "what runs next" would be arbitrary while status answered it confidently
93role or nesting violation
94unknown node or undeclared phase
95a mandatory answer was missing — reversibility, observability, or who a wait is on
96artifact missing or non-conforming
97signal with no citable moment, or quarantined content trying to leave the machine
98goal-linkage violation
99an outward act did not complete; the lines above it name each thing that did not happen

If the wrapper refuses you, fix the input. The exit code is the contract, not an opinion.

The split is deliberate: files are the plan, state is the record. A spec's phase table says what was intended; status says what happened. When they disagree, that disagreement is the finding, surfaced rather than resolved in favour of whichever was read last.

Retrieval

A project's documentation accumulates as it runs, and has to stay findable without being re-read. Three tiers, cheapest first.

TierWhatAnswers
0keel.json + CHARTER.md §1–4. Always read.what this project is, what done means, the boundary, the goals
1reference/INDEX.md — every document with its headings. Verified against disk before use.which document covers X, and which section of it
2live measurement — status, tree, goal-coverage, and going and lookingwhat is true now

The index stores headings, never line numbers, so it survives edits above them. It carries an inputs hash and exits nonzero when stale — a grounding router that answered from a rotted index would be the tool built to prevent stale assertions becoming the most-trusted source of them.

The part that compounds

keel-close-workstream routes real friction into reference/ and rebuilds the index. A portal's session timeout, a counterparty's actual turnaround, a format gotcha that cost an hour — written down at close-out and found by the session six months later that would otherwise rediscover it. Not writing it down does not lose the fact; not indexing it loses the ability to find it.

The signal loop

A project never edits keel. It files a signal — a report, citing project, phase and reproducible evidence. Keel triages it, and because keel is itself a keel project, promotion is just planning.

Issues in, PRs out. A PR from a project session would make it the author of its own fix from a sample size of one, having never read the charter — which is exactly what the queue prevents. A quarantined project files evidence by reference only; the wrapper refuses content with exit 97, because an issue body cannot be unsent.

What keel is not

  • Not a project. If a session here is writing a contract or reconstructing a ledger, it is in the wrong folder.
  • Not a replacement for the earlier workflow it was modelled on. The two do not merge, and a feature shaped for that one estate does not get imported because it exists there.
  • Not a vector store. Retrieval is a drift-checked heading index plus targeted reads. A semantic index that cannot be checked against disk would be a second authority that rots silently.
  • Not a team tool. One person, one reviewer. No assignment, permissions or notifications.
  • Not a second backlog. Signals are the queue. A TODO.md here would be the authority nobody reads.

Untested predictions

These were written before any real project had used keel, as predictions for the first real projects to confirm or break, and none has been marked settled yet. Strike a line through with a date when experience settles it, and file a signal if the fix belongs in keel.

PredictionWhat would disprove itSettled
Depth-on-demand keeps projects comparable, because roles are constrained even though depth is not.Two projects grow shapes that cannot be reported on together, or the "groups" line becomes a formality nobody reads.—
The external actor and waiting are enough to track third parties.A real accountant or auditor produces a state that will not fit — partial delivery, a re-opened request, a chain of hand-offs.—
The three-tier index is enough retrieval.A project gets big enough that heading-level granularity stops narrowing the search usefully.—
Eight gates on a one-sitting phase is proportionate, not ceremony.Express phases get routed around at 11pm, which is the failure mode the ladder exists to avoid.—
n=2 before acting on gap and friction is the right threshold.A real defect sits in the queue for months because only one project ever meets it.—
Preview-then-confirm is sufficient protection for the tracker and for enactment.Something outward-facing lands that should not have — which is an unsafe signal, acting at n=1.—
keel-tracker and keel-documents work.Neither has ever been run against a live board or a real document. They are written and preview-gated; that is all that is known.—
